# One tag-started workflow publishes to PyPI, then creates the GitHub release

A release is one workflow, `.github/workflows/release.yml`, that pushing a tag `v<version>` starts. Its jobs run in `needs:` order: the full CI with the benchmark (`ci.yml`, called with `full: true`), the build, build provenance, the upload to PyPI, and last the GitHub release. We rejected two workflows, a publish workflow and a release workflow, because two primary-source facts make the second one unable to follow the first. PyPI's trusted publishing cannot run from a reusable (called) workflow (docs.pypi.org, trusted publishers troubleshooting; pypa/warehouse#11096 is open), so the upload has to sit in a job of the workflow that the tag starts. And a release created with `GITHUB_TOKEN` does not start another workflow (docs.github.com, "Triggering a workflow"), so a release workflow could not start a publish workflow without a long-lived token. Ordering the jobs inside one workflow gives what the maintainer asked for with no token at all: the GitHub release is created only after the upload succeeded, so every GitHub release has files on an index. The rejected variants are a `publish.yml` started by a published release, `workflow_run`, a check for a green CI run through the checks API, `uv publish` with a separate attestation action, API tokens, and building inside the publish job.

No secret holds a PyPI credential. The publish job has the permission `id-token: write` and nothing else, runs only the download of the build and `pypa/gh-action-pypi-publish`, and trades its OIDC token for a short-lived upload token under trusted publishing, which also attaches PEP 740 attestations. The build job, which runs our code and the build backend, has `contents: read` and no token to trade; the files it makes are attested by `actions/attest` before the upload and are the same files that are uploaded and attached to the GitHub release. Every action is pinned to a commit SHA, no job uses a cache, and `permissions: {}` at the top of the file makes each job ask for what it uses.

The tag decides where a version goes, and the build job checks the tag against the package before anything is built for upload: the tag must equal `v` plus `uv version --short`.

| Tag | Index | Environment | GitHub release |
| --- | --- | --- | --- |
| a release candidate (`v0.1.0rc1`) | TestPyPI | `testpypi` | pre-release |
| `a` or `b` (`v0.1.0a1`) | PyPI | `pypi` | pre-release |
| final (`v0.1.0`, `v0.1.0.post1`) | PyPI | `pypi` | latest release |

Any other form, such as a `.dev` version, stops the build job. The environment `pypi` requires the maintainer's approval and allows only `v*` tags, which is the gate before anything reaches PyPI; the environment `testpypi` allows only `v*` tags and needs no approval. The release notes are the `CHANGELOG.md` section headed with the version, and a pre-release without one takes `## [Unreleased]`. The build job extracts them, so a final tag with no section, or an empty one, fails before the upload and not after it. Both indexes take a trusted publisher that names the repository, `release.yml` and the environment, so renaming the file or an environment breaks publishing until the publishers change too. For the same reason, branch rules that require a successful deployment cannot name `pypi` or `testpypi`: those environments only ever deploy from a tag, after the merge.
