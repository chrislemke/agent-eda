# EDA Python implementation catalogue

> **Status (2026-10-17): backlog, not specification.** The function list, names, signatures and module paths below are proposals that change as each analysis is built. Once an analysis ships, its code and docstring are the source of truth. The shared contracts still apply wherever [AGENTS.md](../AGENTS.md), [GLOSSARY.md](../GLOSSARY.md) and the [ADRs](adr/) don't replace them. Replaced so far: the package is `agent_eda`, not `eda`; analyses take explicit arguments instead of a required `context` (ADR 0004); "analysis" replaces "capability"; numeric family IDs are not part of the public API; results are typed classes per analysis; the status list is shorter (see AGENTS.md).

## How to use this document

Shipped analyses are marked in their function table row. The first cell reads **Implemented in agent-eda 0.1** (or the release that shipped it) with the module, and the contract cell ends with **Implemented differently:**, which lists every point where the shipped analysis departs from the entry. For a marked entry, the code and docstring are authoritative; the rest of the row is history.

1. Find a module in the module index, or an original board family in the family cross-reference.
2. Read its function table together with the shared contracts and type glossary. The module heading defines the import path for every function beneath it.
3. Implement each method against a registered input and result schema. Use the method coverage listed above each family to build that registry.
4. Validate the function-specific calculations, support requirements and failure behavior before registering a capability as available.

For example, `compare_independent_means` belongs to `eda.statistics.comparisons` and `audit_prediction_time_availability` belongs to `eda.evaluation.leakage`.

```python
from eda.statistics.comparisons import compare_independent_means
from eda.evaluation.leakage import audit_prediction_time_availability
```

## Package organization

Each dotted module path maps to a file, for example `eda.statistics.comparisons` maps to `src/eda/statistics/comparisons.py`. Internal helpers can be split into private files as implementations grow. The public module paths and capability names remain stable.

`eda.types` holds the shared records and schemas described below. It adds no public analysis functions to this catalogue. Statistical and domain modules use these records and small private validation utilities. They can reuse `eda.statistics.inference` and related numerical functions without depending on the execution scheduler.

`eda.registry` stores versioned capability metadata and resolves implementations lazily. `eda.execution` calls the registry, enforces the run budget and invokes capabilities. `eda.reporting` validates and combines their results. A domain module must not call `run_standard_eda` to perform a calculation. Sensitivity requests use the same validated dispatcher through an execution service; they must not create recursive module imports.

## Shared implementation contracts

### Signatures and method selection

- Types use Python 3.10+ annotations. Every displayed input has a type. Inputs without defaults are required; `*` introduces keyword-only inputs.
- Every analysis function requires `context: AnalysisContext`. Its alpha, confidence level, seed, policy, dataset roles and resource limits are explicit run inputs. A function must not invent project thresholds, units, entity keys or time cutoffs.
- A `method`, `kind`, `family`, metric or option mapping resolves to a registered schema. Each method declares accepted types, required options, defaults, prerequisites, assumptions, output fields and backend versions. Unknown options are rejected. An optional argument can become required for a selected method.
- `None` means the documented absence or default. Empty grouping sequences mean no grouping. Omitted columns mean all columns eligible for that capability and permitted use; they never override access restrictions.
- Keep the public Python signatures independent of any one statistics backend. Record the backend and version used, and normalize its outputs to the common result contract. A registered method is available only after it is implemented and validated.

### Identity, data preparation and resource limits

- Functions treat inputs as immutable. Return derived arrays or new artifacts rather than altering the caller's DataFrame or source object.
- Use stable observation identities from declared keys or the dataset manifest. Do not join paired arrays, clusters, predictions or artifacts by incidental DataFrame index. Plain arrays must share an explicitly validated order. A `DatasetBundle` binds its identity list to its data and manifest.
- Record eligible, excluded and evaluated counts. Missing-value handling, sentinel replacement, scaling, encoding, binning and weight interpretation must be explicit. A missing result, zero events and zero eligible observations are different states.
- Fit learned preprocessing and diagnostic models only on permitted training observations. Preserve declared pairing, entities, clusters and time windows in evaluation and resampling. A sealed holdout is governed by its configured access policy for every capability.
- Time instants use ISO 8601 with a declared timezone where applicable. Durations and frequencies use a validated, unit-aware package grammar. Spatial distances, survival times and angles retain their units and coordinate conventions.
- Budget checks cover memory, elapsed time, rows, pair counts, permutations, resamples, search combinations and model fits. Check cancellation between bounded work units. Sampling, approximation or truncation requires a recorded rule; an exhausted budget is not permission to change methods silently.
- A result referring to a model, graph, coordinates or a large array includes a URI, format, schema version, checksum, shape and identity ordering. Resolve it only through the run's permitted artifact store. Large outputs remain numeric artifacts; no plots are required.

### Analysis result envelope

All 270 analysis functions and `run_analysis` return `AnalysisResult`. The table's output fields are the capability-specific payload in `result`; the envelope carries shared evidence and execution metadata. Shared helpers with different returns state that type in their table.

| Field | Type | Required behavior |
| --- | --- | --- |
| `schema_version` | `str` | Version of the common envelope and referenced capability payload schema. |
| `request_id` | `str` | Stable identity of this parameterized request within the run. |
| `capability` | `str` | Canonical fully qualified module and function name. |
| `family_ids` | `list[int]` | Original analysis family IDs; shared execution helpers retain the invoked capability's IDs. |
| `method` | `str \| None` | Resolved method identifier, or null for a capability without variants. |
| `parameters` | `JSONMapping` | Resolved inputs/defaults, with dataset or artifact bindings instead of embedded raw data. |
| `execution_status` | `str` | Status from the execution table below. |
| `result` | `JSONMapping` | Method-specific estimates, arrays, counts or audit findings described in the function table. |
| `support` | `JSONMapping` | Input, eligible and evaluated counts; exclusions, missing values, entities, groups and weights where relevant. |
| `findings` | `list[JSONMapping]` | Each finding has an ID, a concise claim, evidence field paths and an assessment such as descriptive, suspected, violation, passed or unknown. |
| `uncertainty` | `JSONMapping` | Procedure, level, interval/test field references, assumptions and unavailable-inference reasons. Record confidence versus credible intervals explicitly. |
| `assumptions` | `list[JSONMapping]` | Assumption ID, description, evidence and state: checked, violated, supplied or untestable. |
| `limitations` | `list[JSONMapping]` | Coded limitations and the fields or interpretations they affect. |
| `artifacts` | `list[JSONMapping]` | Versioned references to permitted large numerical outputs or fitted state. |
| `execution` | `JSONMapping` | Start/end times, duration, backend versions, resolved seed, budget usage, sampling, approximation and source/config/code versions. |
| `errors` | `list[JSONMapping]` | Structured error code, message, relevant field path and retryability. Empty for successful execution. |

All records must serialize as strict JSON. Non-finite and undefined values become `null` with a reason tied to the field path. Never encode infinity as a large finite sentinel. Include empty lists or explicit nulls where the registered schema requires them. Statistical intervals and p-values are present only when their calculation is supported by the data design. Reporting that inference is unavailable is preferable to substituting an invalid independence assumption.

### Execution status and error handling

| Status | Meaning |
| --- | --- |
| `completed` | The requested computation finished. Its audit findings can still contain violations or unknowns. |
| `partial` | Some declared subresults completed and others could not. Identify every incomplete component and its reason. |
| `not_selected` | The capability was available in the plan but not requested for this run. This is a coverage record, not a successful calculation. |
| `not_applicable` | The known data or task lies outside the capability's intended domain. |
| `missing_prerequisites` | Required columns, metadata, support, dependencies or fitted artifacts are unavailable. |
| `unsupported_method` | The requested variant or combination is not implemented for these inputs. |
| `budget_exceeded` | The resource estimate prevented execution or the run reached a limit. Retain completed subresults only as explicitly partial evidence. |
| `blocked_by_policy` | The requested data access, purpose or operation is not permitted by the supplied policy. |
| `cancelled` | Execution stopped on an explicit cancellation signal. |
| `failed` | Invalid inputs or a numerical/runtime error prevented a valid result. Include a structured error code and diagnostic evidence. |

Validate malformed inputs before numerical execution. Direct Python APIs may raise documented validation errors; the executor converts them into structured failed results. Expected prerequisite or applicability outcomes should return explicit status records. Shared helpers that return ordinary metadata raise structured validation/I/O errors on failure; their gateway adapter must serialize those errors. Never swallow an exception and return an empty successful result.

Audit conclusions are separate from execution status. A permission or leakage audit can finish successfully and report a violation. A check with missing timing, lineage or access records remains unknown. Statistical suspicion alone does not establish leakage, causation or a missingness mechanism.

### Reproducibility and inference

Derive child seeds deterministically from the run seed and stable request identity. Store fitted preprocessing, method settings, source/configuration hashes and backend versions. Stable ordering applies to named outputs, category levels and artifact identities. Stochastic or approximate methods report their variability and tolerances; a seed alone does not guarantee identical results across environments.

Each inference method declares its estimand, sampling unit, null hypothesis or posterior model, and tail convention. Pairing, cluster dependence, time blocks and weights must use supported formulas or resampling designs. Refit learned quantities inside resampling when the estimand requires it. Adaptive analysis choices and all executed tests feed the multiplicity/history record.

### Capability registration checklist

For each implemented method, register its exact method identifier and option schema, required columns/metadata, permissible preprocessing, minimum support, cost estimate, result schema and dependency versions. Add numerical reference checks and cases covering nulls, empty support, constants, ties, singularity or boundary behavior as relevant. Check alignment and prohibited fitting for methods that learn from data. Do not mark a method available solely because its public function exists.

The catalogue specifies the function boundaries and required behavior. Method-specific options and result schemas must be made explicit in the registry before execution; the `JSONMapping` inputs are extension points with validation, not unrestricted keyword bags or executable expressions.

## Input and return type glossary

Named records live in `eda.types`. JSON callers pass schema-validated records and artifact bindings. In-process callers may use equivalent typed Python records. Arrays and fitted objects are serialized through artifact references when needed.

| Type | Definition |
| --- | --- |
| `DataFrame` | A pandas.DataFrame containing tabular observations. Column roles, logical types and units come from project metadata; callers do not rely on the DataFrame index as an implicit identity key. |
| `ArrayLike` | numpy.typing.ArrayLike, including numeric sequences, NumPy arrays or compatible Series. Inputs must have the dimensionality and ordering required by the selected method; JSON clients provide arrays or artifact bindings. |
| `Sequence[T]` | An ordered collections.abc.Sequence of T values, usually a list or tuple. Ordering is meaningful for paired inputs, category levels, coordinates, group contrasts and hypothesis identifiers. |
| `Mapping[K, V]` | A collections.abc.Mapping, usually a dict, from keys of type K to values of type V. |
| `Path` | pathlib.Path for a local filesystem location. A str may also identify a supported source or destination URI. |
| `JSONValue` | A JSON scalar, list of JSONValue items or dict[str, JSONValue]. Numeric values must be finite. Non-finite or undefined analysis outputs become null with an explicit reason. |
| `JSONMapping` | Mapping[str, JSONValue]. Metadata, method_options and other parameter mappings must follow the selected capability's registered schema; they are not arbitrary Python expressions. |
| `AnalysisResult` | A JSON-compatible result record with capability, method, parameters, execution status, statistics or estimates, findings, uncertainty where estimable, assumptions, limitations, support and reproducibility metadata. Large arrays or fitted objects may use artifact references with schema and checksums. |
| `AnalysisContext` | A shared run record containing run_id: str, project_config: JSONMapping, dataset_roles: Mapping[str, str], alpha: float, confidence_level: float, random_seed: int, budget: JSONMapping and policy: DataPolicy. It also carries source/config versions and relevant sampling or execution metadata. These values are explicit project/run inputs, not silently chosen statistical defaults. It also binds dataset identities and artifact resolution to the run. Missing analysis-design information is a prerequisite gap rather than permission to infer it. |
| `ColumnSpec` | A typed column record with dtype: str and optional role: str, unit: str, nullable: bool, allowed_values: Sequence[JSONValue], bounds: JSONMapping and datetime or precision constraints. |
| `DataContract` | A typed record with columns: Mapping[str, ColumnSpec], keys: Sequence[Sequence[str]], rules: Sequence[RuleSpec] and optional expected row-count, granularity or relationship constraints. |
| `DataPolicy` | A typed policy record declaring column access and allowed uses, dataset-role restrictions, permitted external processing and retention requirements. Reading, model use and evaluation use are separate permissions. |
| `RuleSpec` | A declarative rule record with id: str, kind: str, columns: Sequence[str] and parameters: JSONMapping. kind refers to a registered rule or predicate; free-form Python execution is not part of this record. |
| `RelationshipSpec` | A relationship record with left_table: str, right_table: str, left_keys: Sequence[str], right_keys: Sequence[str] and expected_cardinality: str. Cardinality explicitly declares one-to-one, one-to-many, many-to-one or many-to-many expectations. |
| `SamplingSpec` | A sampling-design record with method: str, strata_columns: Sequence[str], cluster_columns: Sequence[str] and optional inclusion-probability or weight columns, population totals and stage definitions. |
| `ResamplingSpec` | A resampling record with scheme: str, n_resamples: int and method-specific grouping, strata, permutation or deletion fields. Paired, clustered and time-block schemes explicitly define their exchangeability or resampling units; exact enumeration is explicitly requested. |
| `DistanceSpec` | A distance record with metric: str, scaling: JSONMapping, column_types: Mapping[str, str], optional column_weights: Mapping[str, float] and parameters: JSONMapping. It declares treatment of missing and categorical values. |
| `ModelSpec` | A model or simulation specification with kind: str and parameters: JSONMapping, plus preprocessing or family/link settings where applicable. It identifies a registered diagnostic estimator, clustering algorithm or null-data generator rather than arbitrary code. Method-specific options include the link function, solver, preprocessing and fitting budget when relevant; they are validated before fitting. |
| `EvaluationSpec` | An evaluation record declaring dataset roles or split assignments, splitting method, grouping and time columns, fold count and method parameters. It records where fitting is allowed and how evaluation observations remain separate; sealed final-holdout use requires the declared project policy. |
| `ModelArtifact` | A fitted diagnostic-model reference with uri: str, feature schema, task/family metadata, training manifest and permitted evaluation or prediction references. It provides the model state required by later diagnostics without embedding a non-JSON estimator in the report. |
| `AnalysisRequest` | A callable-capability request with name: str, dataset_bindings: Mapping[str, str] and parameters: JSONMapping. Shared context is supplied separately by the current run. |
| `StatisticSpec` | A registered statistic request with name: str, columns: Sequence[str] and parameters: JSONMapping. It defines the estimand and any group or contrast orientation used inside bootstrap, permutation or related procedures. |
| `SurvivalSpec` | A survival-data record declaring duration or interval-bound columns, event coding, optional delayed-entry column, censoring kind and time units. The selected estimator must support that censoring and truncation design. |
| `Graph` | A supported networkx.Graph or networkx.DiGraph. Direction, node identities, edge weights and any multiedge aggregation are explicit in graph construction metadata. |
| `FunctionalData` | A curve-data record with curve_ids: Sequence[JSONValue], values: Sequence[ArrayLike], grids: Sequence[ArrayLike] and metadata: JSONMapping. Each curve is aligned with its declared observation grid; common and irregular grids are distinguished. |
| `CausalSpec` | A record of supplied causal structure, treatment/outcome/covariate columns, temporal ordering, identifying assumptions and optional negative controls. Untestable assumptions remain labeled assumptions. |
| `ScenarioSpec` | A scenario record with name: str, parameter_overrides: JSONMapping and registered data-variation instructions. Supported axes include sampling, seeds, thresholds, windows, missing-data assumptions, measurement error and diagnostic transformations. |
| `DatasetBundle` | In-process return record with `data: DataFrame`, `observation_ids: Sequence[JSONValue]` and `manifest: JSONMapping`. The manifest includes source identity, schema, row alignment and any sampling details. The gateway representation returns a permitted dataset artifact reference and its manifest instead of a DataFrame. |

Optional specialized analyses declare their own metadata. |
