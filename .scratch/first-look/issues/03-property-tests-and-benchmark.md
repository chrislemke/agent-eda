# 03: Property tests and benchmark for every analysis

**What to build:** A maintainer runs `uv run pytest`, and every registered analysis runs on generated DataFrames full of edge cases. A new analysis then meets the contract or fails loudly, without anyone writing new property tests for it. A separate opt-in benchmark times every analysis on a deterministic DataFrame of 1M rows and 100 mixed columns.

Both loop over `ae.list_analyses()` and use one call recipe per analysis, kept in the tests. The fixtures, the strategy and the recipes written here become the pattern for later slices.

Read these sections of `.scratch/first-look/spec.md`: Performance, and test groups 4 and 9, What makes a good test here and Warning policy under Testing Decisions. Covers user stories 44, 115, 118 and 119.

**Blocked by:** 02-summarize-numeric-and-column-rules

**Status:** ready-for-agent

- [x] A mixed-dtype DataFrame strategy generates floats with NaN and infinity, nullable integers, bool and boolean, object strings including empty and whitespace-only ones, pandas 3 strings, categoricals with unused categories, naive and time-zone-aware datetimes, and pyarrow-backed columns. It also generates zero rows, one row, zero columns, constant columns and all-missing columns. It works on pandas 2.2 and on 3.x.
- [x] For every analysis in `ae.list_analyses()` and valid generated input, these properties hold:
  - no unexpected exception
  - the status is one of the analysis's declared statuses
  - `to_json()` is strict JSON

  - the input DataFrame keeps its values, dtypes, index, columns and `attrs`
  - no warning escapes
  - the printed text stays within 40 lines and 120 characters per line
- [x] Each analysis has a call recipe in the tests that builds valid arguments for a generated DataFrame. A registered analysis without a recipe fails the suite with a message that says to add one.

## Comments

What this ticket settled that the spec left open:

- **Where things live.** `tests/strategies.py` holds the DataFrame strategy `data_frames()`, its 34 column kinds in `KINDS` and the fixed frames `EDGE_FRAMES` and `LABEL_EDGE_FRAMES`. `tests/recipes.py` holds `RECIPES` and the helpers for writing a recipe. `tests/test_properties.py` checks the contract, and `tests/test_benchmark.py` builds the benchmark frame and times every analysis. `tests/conftest.py` holds the Hypothesis profiles and the benchmark's report. The helpers import only `agent_eda`, and `test_suite_rules.py` now checks every module in `tests/`, not only `test_*.py`.
- **Recipes.** A recipe is `Recipe(required=..., options=..., any_column_labels=...)`. `required(df)` returns the arguments that have no default, built from the DataFrame. The benchmark passes exactly these, so every option keeps its default. `required` returns None when the DataFrame allows no valid call, such as a target column in data without columns. Hypothesis then discards the example, and the edge-case test skips the frame. `options(df)` returns a strategy for further arguments, which may also replace required ones. `optional(**strategies)` leaves each option out some of the time, `choices()` reads a Literal's values from the signature, and `names()` with `column_lists()` draws column names. Only describe_dataset sets `any_column_labels=True`, which lets the strategy draw repeated, colliding, missing and MultiIndex column labels. For every other analysis, valid input has unique labels, distinct as strings, though they can still be integers, long, blank or full of control characters. Without a recipe, `recipe_for(name)` fails with "<name> has no call recipe. Add one to RECIPES in tests/recipes.py: ...", and `test_every_analysis_has_a_call_recipe` reports it once per analysis.
- **Properties.** Two tests check them for every analysis. `test_every_analysis_keeps_the_contract_on_generated_data` runs 50 Hypothesis examples, and `test_every_analysis_keeps_the_contract_on_edge_cases` runs the fixed frames with the required arguments only. Both go through `check_contract`, which calls the analysis twice on the same DataFrame object, so the second call sees whatever the first left behind. The input is valid, so "no unexpected exception" means no exception at all, an `AgentEDAError` included. "No warning escapes" covers the call, `str()`, `to_json()` and `to_frame()`. DeprecationWarning and FutureWarning still raise there, as everywhere in the suite. The input check compares the values exactly, the dtypes, the class and labels of the index and columns, `attrs` and `flags`. The text check splits with `splitlines()`, so a stray line separator counts as a line break.
- **Strategy.** `data_frames()` draws 0 to 8 rows and 0 to 6 columns. Each column has one of 34 kinds: NumPy, nullable and pyarrow numbers and booleans; Float64 storing NaN as a value; sparse floats; object, python, pyarrow and pandas 3 `str` text; objects of mixed types and of lists and dicts; categoricals with unused categories; naive, UTC and Europe/Berlin datetimes; pyarrow timestamps, dates and durations; timedeltas; pyarrow decimals and lists. Each column also has a shape, one of any values, ties, one constant value or all missing. Floats favour NaN, ±inf, ±0.0 and the extremes. Text favours empty and whitespace-only strings, case and space variants, stand-ins such as "N/A", and characters of 1, 2 and 4 bytes. The row index is a range, shuffled, repeated, text, float with NaN, datetime with NaT, period, categorical with an unused category or a two-level MultiIndex. Some frames carry `attrs`. On pandas 2.2, `string[pyarrow_numpy]` stands in for pandas 3's `str`. `test_generated_frames_cover_every_dtype_family_and_shape` draws 200 frames and fails if a family or shape this ticket lists never comes up. It caught that `st.floats()` alone almost never gives infinity.
- **Fixed frames.** Every run checks these: nothing; no rows; no columns; one row, four rows, constant and all-missing columns of every kind; 136 columns, more than the printed table shows and the record keeps; and object columns sharing non-ASCII strings. describe_dataset also gets repeated, colliding, missing and MultiIndex column labels.
- **Hypothesis profiles.** `tests/conftest.py` loads `suite` by default. It is derandomized, has no deadline, runs 50 examples and prints the blob that replays a failure. `thorough` is the same with 1,000 examples, run with `uv run pytest --hypothesis-profile=thorough`. Every run, under any `PYTHONHASHSEED`, draws the same examples, and they change only when a test or Hypothesis changes. `.gitignore` now lists `.hypothesis/`. The property tests take about 1.4 s, and `uv run pytest` about 4.5 s with the latest versions and 7.3 s with the minimum ones.
- **Benchmark frame.** `benchmark_frame()` in `tests/test_benchmark.py` draws from `numpy.random.default_rng(0)`. It has 25 float64 columns with NaN, every 3rd rounded to one decimal and every 5th with 0.1% inf and 0.1% -inf; 15 Int64, 20 text and 15 categorical columns with 2 up to 1,000,000 distinct values; 7 bool and 3 boolean columns; and 13 naive and 2 time-zone-aware datetime columns. 4.95% of the values are missing. The 3 all-distinct text columns have none, like IDs. Text is object on pandas 2 and `str` on pandas 3. The builder makes it in row order. A column with fewer than 10,000 distinct labels shares one object per label, and the others hold one object per row. `test_the_benchmark_frame_has_the_specified_columns` checks the dtypes, the infinities, the cardinalities and the missing share.
- **Benchmark.** `uv run pytest -m benchmark` runs it, as the README says. `addopts` deselects the `benchmark` marker, and `-m benchmark` overrides that. Each analysis gets its recipe's required arguments and runs once on the first 1,000 rows to load what it imports. The benchmark then times one call on the whole frame and fails it at 5 seconds or more. threadpoolctl and `pyarrow.set_cpu_count` limit BLAS and pyarrow to 2 threads, like the target's 2 vCPUs. At the end of the run, a `benchmark` section prints the frame, the versions, each analysis's time and status, and the peak memory.
- **New dev dependencies.** `hypothesis>=6.170.1`, and `threadpoolctl>=3.7.0`, which scikit-learn already depends on and the benchmark imports.

The bug the properties found, now fixed:

- **describe_dataset gave different JSON for two identical calls.** It happened when an object column shared a non-ASCII string object with a column holding only text. The first column's `memory_bytes` grew from one call to the next. Counting the second column's distinct values went through pandas' string hash table, which makes Python cache a UTF-8 copy inside each string, and `sys.getsizeof` counts that copy. Any earlier work on the strings, such as a pyarrow conversion, moved the number too, which is the limit ticket 01 recorded. Now a non-ASCII `str` counts as Python stores it without that copy, a 56-byte header measured at import plus 1, 2 or 4 bytes for each character and the terminator. Every other object counts its `sys.getsizeof`, as in pandas. Object columns and python-backed string columns take their missing count, distinct count and memory from one `pd.factorize` pass, which sizes each distinct string once. On fresh data the numbers equal pandas' `memory_usage(deep=True)` for every fixed frame and a 10,000-row benchmark frame, on both pandas versions. The regression tests are `test_identical_calls_agree_when_columns_share_a_non_ascii_string` and `test_memory_of_text_ignores_the_utf8_copy_python_caches`, the second for characters of 1, 2 and 4 bytes. Random fuzzing found the bug with seed 11 and frames of up to 30 rows. The default derandomized run never drew that arrangement, so I added the "shared strings" frame, which fails on the old code.
- Nothing else failed. Besides the default and `thorough` runs on both version sets, random runs of the same checks passed 26,000 examples per analysis after the fix. They used 6 seeds and frames of up to 30 or 60 rows and 8 columns, on pandas 3.0.6, on pandas 2.2.0 with numpy 1.26.0, and on Python 3.14. summarize_numeric never failed.

Measurements, two runs each, on an Apple M3 Max with 12 performance and 4 efficiency cores and 128 GiB under macOS 27.0.1, with Python 3.12.11 and 2 threads:

| Versions | describe_dataset | summarize_numeric | Frame built in | Peak memory |
| --- | --- | --- | --- | --- |
| pandas 3.0.6, numpy 2.5.4, pyarrow 26.0.0 | 0.80 and 0.82 s | 1.24 and 1.24 s | 2.9 s | 1.77 GiB |
| pandas 2.2.0, numpy 1.26.0, pyarrow 14.0.1 | 1.82 and 1.84 s | 1.42 and 1.45 s | 2.4 s | 2.23 GiB |

- On pandas 2.2.0, describe_dataset took 2.61 s on the benchmark before the fix. The single factorize pass that ticket 01 suggested cut that to 1.8 s. On ticket 01's harder frame, with 25 object-text columns of which 5 are all distinct, it went from 3.2 to 3.4 s down to 2.5 s. Ticket 01 measured 5.95 s on its own build of that frame. A column of 1,000,000 distinct non-ASCII strings costs 0.26 s, against 0.15 s for ASCII ones, on both pandas versions.
- The slowest case, describe_dataset on pandas 2.x, leaves a margin of 2.7 times to the 5-second target on this machine.

Not checked locally: the target machine, a 2-vCPU, 8 GB AgentCore session, whose per-core speed against an M3 Max core nobody has measured; and Linux. Ticket 05's CI runs the benchmark on 2 CPUs.

Each analysis ticket that follows adds a `Recipe` to `RECIPES` in `tests/recipes.py`, or the suite fails and says so. `required` must give a valid call on any generated frame and on the benchmark frame, for example by picking the first suitable column, and return None when there is none. `options` should cover every other parameter, `columns` included. The property tests, the fixed frames and the benchmark then pick the analysis up from `ae.list_analyses()`, and its time joins the benchmark report. Set `any_column_labels=True` only for an analysis that accepts the column labels other analyses reject, as describe_dataset does. Ticket 08 adds the no-leak property next to `check_contract`, for the analyses whose `ae.list_analyses()` entry supports masking. The generated text is too generic to search a result for, so that property should give sensitive columns distinctive values.
