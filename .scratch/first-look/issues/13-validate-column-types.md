# 13: validate_column_types

**What to build:** An agent declares the logical type it expects for each column and calls `ae.validate_column_types(df, schema=...)`. For each declared column it learns how many values already have that type, how many convert exactly, how many are invalid and how many are missing, with example row IDs and values for the invalid ones. The package never changes the data to find this out. A declared column missing from the data comes back as a violation, so checking a broken file still completes.

The analysis shares infer_column_semantics's parse rules, so the two never disagree on what parses. It lives in `agent_eda.data.validation`.

Read these sections of `.scratch/first-look/spec.md`: the validate_column_types entry under The first-look analyses, Row IDs, and Project, data policy and masking. Covers user stories 86 to 89.

**Blocked by:** 08-project-and-masking, 12-infer-column-semantics

**Status:** done

- [x] `schema` is required and maps column names to a logical type or a `ColumnSpec`. `id_column`, `project` and `mask_sensitive` work as in find_duplicate_rows.
- [x] Per declared column, the result gives the expected logical type, the observed dtype, whether the column is present, and four counts: compatible values, already stored as that type; convertible values, which convert exactly without changing meaning, such as "42" or 42.0 for integer, or text in ISO 8601 or the declared `datetime_format` for datetime; invalid values; and missing values.
- [x] Invalid values come with up to 10 example row IDs and 5 distinct example values, each with its total.
- [x] The result lists the undeclared columns.
- [x] Invalid values, a declared column missing from the data and missing values in a column declared non-nullable each give a violation. A clean column gives a passed finding, and a column without values to check gives an unknown one.
- [x] Nothing is coerced, and the data never changes.
- [x] The declared statuses are `completed` and `failed`. The status is `completed` also when declared columns are missing from the data.
- [x] validate_column_types and infer_column_semantics share one implementation of the parse rules, so they agree on which text parses as a number, an integer, an ISO 8601 date or a boolean.
- [x] With masking on, example values from sensitive columns and row IDs from a sensitive `id_column` become placeholders.
- [x] The docstring has the seven sections in order and passes the contract tests.
- [x] The property suite has a call recipe for it, and the properties hold, including the no-leak property.
- [x] With default arguments it finishes in under 5 seconds on the benchmark DataFrame.
- [x] `ae.search_analyses("check data types against a schema")` returns it first. The row joins the search acceptance table, and every earlier row still passes.
- [x] Its catalogue entry is marked implemented, with its differences from the catalogue noted, among them "convertible" instead of "parseable".
- [x] Nearby analyses mention it in `When to use:` and `See Also:` where it is the better choice.

## Comments

What this ticket settled that the spec left open:

- **Where things live.** The analysis sits in `agent_eda.data.validation` next to infer_column_semantics. `agent_eda/_conversions.py` holds the rules: `check_column` sorts a column's values into compatible, convertible, invalid and missing. `_parse.read_datetime_format` adds the declared-format rule to the shared parse rules, which ticket 12 left to this ticket. `ValidateColumnTypesResult`, `ValidateColumnTypesColumn` and `InvalidValue` sit in `agent_eda.results`.
- **Compatible means stored as the declared type**, by dtype or, in an object column, by Python type: booleans as boolean, ints as integer, floats as float, strings as text, datetimes and dates as datetime, durations as timedelta, and the values of a categorical dtype as categorical. So 42.0 is convertible to integer, as the ticket says, and 42 is convertible to float the same way. **What converts**: to boolean, numbers equal to 0 or 1 and boolean text; to integer, whole floats and decimals and whole-number text; to float, any other number and number text; to datetime, ISO 8601 text or text in the declared `datetime_format`; to categorical, any value that can be hashed; to text, booleans, numbers, datetimes and durations. Nothing converts to timedelta, since the shared rules have no duration text and a number has no unit; adding a rule there would change infer_column_semantics too. Other objects (bytes, periods, lists) are invalid for text, and unhashable ones for categorical. A category of a categorical dtype converts to whatever its label is or converts to. Decimals count as whole the way infer_column_semantics decides it, through float64, so the two agree. Integers beyond 2^53 still convert to float.
- **One implementation of the parse rules.** Text goes through `_parse.read_texts` once per distinct string, the same function infer_column_semantics reads with. A property test, `test_accepts_the_values_infer_column_semantics_reads_as_each_type`, checks over generated frames of every kind that for boolean, integer, float and datetime the share validate_column_types accepts equals infer_column_semantics' `boolean_share`, `integer_share`, `number_share` and `datetime_share`, and that both count the same non-missing values; a second one does the same over strings near the edges of the rules. Breaking one rule in `_conversions.py` on purpose failed the first property.
- **Values of different types are read apart.** pandas counts 1, 1.0 and True as one value, but for 'integer' they are compatible, convertible and invalid. In an object column whose values aren't all text, values are grouped by type and value, and `invalid_distinct_count` counts distinct invalid values that way.
- **Missing** means what pandas isna() counts, plus NaN that a float column stores as a value, as in infer_column_semantics and summarize_numeric, with the same `nan_counted_as_missing` limitation.
- **`datetime_format`.** ISO 8601 text converts whether or not a format is declared, as the ticket says. A format is read with `datetime.strptime` after stripping surrounding whitespace, ASCII only like every other rule, with month and day names in the process's locale. strptime reads each distinct text, about 4 seconds per million distinct values matching the format and 1.7 seconds per million that don't; the docstring says so. pandas' vectorized parser would be faster, but on pandas 2.2 it turns dates beyond 2262 into NaT, and how lenient its ISO path is for ISO-like formats I couldn't verify, so it would break "convert exactly".
- **The entries.** One per declared column, keyed by name in declared order, with the declaration (`declared_logical_type`, `nullable`, `datetime_format`), `present`, `dtype`, the four counts (`compatible_count`, `convertible_count`, `invalid_count`, `missing_count`, which add up to the rows) and the invalid values. The analysis declares only completed and failed, so entries carry no status of their own. Instead each has an `assessment`, violation, unknown or passed, as its findings give it. A declared column the data lacks has `present` false and a null dtype and null counts, with the new limitation code `column_not_in_data`.
- **Invalid values.** `invalid_row_ids` holds the first 10 rows with an invalid value in row order, and `invalid_values` the first 5 distinct ones, each with `value`, `value_type` and `count`. The result object keeps only those, with the totals in `invalid_count` and `invalid_distinct_count`, through `_Cap(total=...)`. `to_frame(table='invalid_values')` lists every distinct invalid value with its count; it has no row IDs, since keeping the position of every invalid row could cost hundreds of MB, and the values find the rows with `isin`. Examples come in level order, as summarize_categorical orders levels: most frequent first, then by value. That reuses `_levels` for ordering, masking (`mask_levels`) and the table (`levels_frame`), through a new `levels_of(values, counts)`. LEVEL_ORDER orders Timestamps by their string form, which `_levels` did one label at a time: 945,000 tied invalid datetimes took 4.9 s. `_levels` now orders datetime64 dtypes with vectorized keys that give the same order, in about 0.05 s. Without a time zone that is the order in time; with one, the local time and then the offset as text, which parts from the order in time only where clocks go back, as `test_invalid_datetimes_that_tie_follow_their_string_forms` pins. Duration and pyarrow timestamp dtypes still take the per-label path.
- **Findings**, in this order: `invalid_values`, `declared_columns_missing` and `non_nullable_missing_values` (violations), `unchecked_columns` (unknown: present but without a non-missing value), `convertible_values` (descriptive) and `valid_columns` (passed). Convertible values don't fail a column: it passes, and `convertible_values` says to convert them before use, which answers the catalogue's "a value that can be coerced is not automatically valid under a strict contract" without a threshold. A column whose values are all missing and that is declared non-nullable gets both `non_nullable_missing_values` and `unchecked_columns`. `declared_columns_missing` shares its claim, with the closest names, with infer_column_semantics through `_missing_columns_claim`. Claims stay short so each printed line fits 120 characters.
- **Errors.** An empty schema raises `InvalidArgumentError`, since it declares nothing to check. A call without schema raises `invalid_call` from the registry, which treats an option without a default as required. Ticket 15 built the same in parallel; the merge kept ticket 15's code and extended its message to the values of a mapping or list option, so it says that each value in schema is one of the seven logical types or a ColumnSpec. Schema keys follow the column rules of ticket 10's mapping normalization, values are validated as in infer_column_semantics, and id_column goes through `read_row_ids`.
- **Registry.** pydantic warns that an arguments field named `schema` shadows `BaseModel.schema`. `_spec` now silences exactly that UserWarning while it builds the arguments model, as ticket 12 suggested.
- **Masking.** The invalid values of a sensitive column become `<masked k>`, numbered in level order per column, in the entries, the text and `to_frame()`. Row IDs from a sensitive id_column become placeholders too. When id_column is also declared, a row ID equal to one of its invalid values takes that value's placeholder, and other IDs are numbered on from there in result order, so one value shows as one placeholder everywhere. `masking.columns` lists the columns whose invalid values or row IDs the result shows. Index labels are never masked.
- **Text.** The facts define compatible, convertible and invalid in one line, then say where row IDs come from and which columns weren't declared. The table lists the declared columns, violations first and then in declared order, with the declared type (", not null" when declared non-nullable), the dtype or "not in the data", the four counts and the invalid examples with their counts; placeholders print without quotes. The footer names the invalid_values table. The wording of the first fact and the footer keeps the docstring example within ruff's 124-character limit.
- **Search.** Tags: schema, data contract, validation, declared types, data types, expected types and invalid values. "check data types against a schema" scores 12 here against 4 for infer_column_semantics, and "invalid values" now finds this analysis first. "nulls per column" still finds profile_missing_values first, by 7 to 5, since "column" is in this analysis's name. infer_column_semantics', describe_dataset's and profile_missing_values' `When to use:` and `See Also:` point here.
- **Tests and recipe.** The recipe's `required` declares every column, the seven logical types in turn by position, so the benchmark runs the parse paths on all 20 text columns. `options` draws schemas with ColumnSpecs, nullable, datetime formats and a column the data lacks, plus id_column and masking; `declared_schemas` gained `min_size` and specs with a datetime format, which infer_column_semantics' recipe now draws too. `sensitive_options` declares the sensitive columns as boolean or timedelta, which every marked value fails, and may make one of them id_column. Disabling the masking of values, and separately of row IDs, failed the no-leak property each time. `test_contract.py`: `schema` joins `KEYED_BY_COLUMN`, and `keyed_by_str` now reads a mapping annotation that isn't a union, as a required option has.
- **Glossary gap.** "Compatible", "convertible" and "invalid value" are defined in the docstring and field descriptions, but not in GLOSSARY.md; noted for /domain-modeling.
