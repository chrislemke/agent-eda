# 08: Project and opt-in masking

**What to build:** An agent handling personal data declares sensitive columns in a Project and switches masking on, either for every call through the Project or for one call with `mask_sensitive=True`. Numbered placeholders then replace the raw values of those columns in everything the agent reads, while counts, shares and statistics stay.

This ticket adds `ae.Project` and `ae.DataPolicy` and brings masking to summarize_categorical and find_duplicate_rows. The later analyses that can show raw values build on it. Masking is a guardrail against accidental exposure, not anonymization and not access control, per ADR 0001.

Read these sections of `.scratch/first-look/spec.md`: Project, data policy and masking, and test groups 4 and 7 under Testing Decisions. Covers user stories 67 and 70 to 78.

**Blocked by:** 06-summarize-categorical, 07-find-duplicate-rows-and-row-ids

**Status:** done

- [x] `ae.Project` is a frozen pydantic model that rejects unknown fields, with an optional `name` and a `data_policy`. `ae.DataPolicy` has `sensitive_columns`, default none, and `mask_sensitive`, default false. Setting `mask_sensitive` without sensitive columns raises `InvalidArgumentError`. Dataset roles stay out of this slice.
- [x] Invalid Project or DataPolicy arguments raise `InvalidArgumentError` in the package's message format, never a raw pydantic error.
- [x] summarize_categorical and find_duplicate_rows accept `project=` and `mask_sensitive=`. A per-call True or False wins. Otherwise the Project's setting applies, and without a Project nothing is masked. A per-call True without a Project that declares sensitive columns raises `InvalidArgumentError`.
- [x] Masking stays off by default, even when sensitive columns are declared.
- [x] With masking on, numbered placeholders per column, in result order, replace the category levels of sensitive columns in summarize_categorical and the row IDs taken from a sensitive `id_column` in find_duplicate_rows. The placeholders, `<masked 1>`, `<masked 2>` and so on, reveal neither content nor length. Counts, shares and numeric statistics stay.
- [x] Index labels are never masked. The docs tell the agent to pass a non-sensitive `id_column` when the index holds sensitive values.
- [x] Masking covers the printed text, `to_dict()`, `to_json()` and `to_frame()` alike. The result's `masking` field records whether masking was applied and to which columns.
- [x] `ae.list_analyses()` and `ae.describe_analysis()` report masking support for both analyses, and `describe_analysis()` says that they can show raw values.
- [x] The property suite gains a no-leak property for every analysis that supports masking: with masking on, no raw value from a sensitive column appears in the printed text, `to_json()` or `to_frame()`.
- [x] The docstrings and the Project docs call masking a guardrail against accidental exposure, not anonymization and not access control.
- [x] Tests cover a Project built in code, every combination of the masking resolution, and the error for masking without sensitive columns.
- [x] `uv run ruff check .`, `uv run ruff format .`, `uv run ty check` and `uv run pytest` pass, on the latest and on the minimum dependency versions.

## Comments

What this ticket settled that the spec left open:

- **Where things live.** `Project` and `DataPolicy` sit in the public module `agent_eda.project`, exported as `ae.Project` and `ae.DataPolicy`. The masking code the analyses share is in `agent_eda/_masking.py`, whose docstring lists the steps an analysis takes. `agent_eda.results` gained the `Masking` record and `MaskableResult`, the base of every result class whose analysis supports masking. `_text.placeholder(n)` writes `<masked n>`. The work started on first-look at 6eba92c and moved to 583cd66, after tickets 10, 12, 14 and 16 landed, before the commit.
- **Project and DataPolicy.** Both are frozen, strict pydantic models that reject unknown fields and take their fields by keyword only. `sensitive_columns` stores a tuple of names, so a Project is immutable and hashable. It takes names the way the analyses' `columns` does: any ordered list-like, a single name (bytes too), or labels that aren't strings, named by their string form. A set works too, sorted by name, since order means nothing there. A name listed twice raises, as in `columns`. A dict raises with the form to use, and so do a Series and a DataFrame, whose values would otherwise become names and show up in messages and results; the message names neither. None declares no sensitive column. `data_policy` takes a DataPolicy, a dict of its fields or None, which means the default policy. Names the data lacks are allowed, because one project can span several datasets.
- **Errors.** Every way to build one raises `InvalidArgumentError` in the package's format, through ticket 12's `invalid_message` and `unknown_name_message`: calling it, `model_validate()`, `model_validate_json()`, `model_validate_strings()` and a dict of its fields given as `project=` or `data_policy=`. A dict key that isn't a string raises before pydantic would pass it to `__init__` as a keyword, which raised a bare TypeError. An unknown field, a key that isn't a string or a positional argument has code `invalid_call`, a bad value `invalid_argument`. A DataPolicy field given to the Project, such as `ae.Project(sensitive_columns=...)`, points to `ae.Project(data_policy=ae.DataPolicy(...))`. A DataPolicy passed as `project=` says to put it in a Project. The registry now re-raises the package's own error about a whole option with its own code, so an unknown field in a dict given as `project=` keeps `invalid_call`. Assigning to a field still raises pydantic's frozen error, as results and ColumnSpec do, since that is no argument.
- **Resolution.** Each masking analysis calls `_masking.resolve_masking(analysis, project, mask_sensitive)` before any computation and gets a `MaskingDecision`. A per-call True or False wins. Otherwise the project's `data_policy.mask_sensitive` applies, and without a project nothing is masked. Masking with no sensitive column raises, with one message for a call without a project and one for a project that declares none. The check also catches a policy built with `model_copy()` or `model_construct()`, which skip validation.
- **The `masking` field** holds `applied`; `decided_by`, which is `mask_sensitive`, `project` or `default`; `columns`, the sensitive columns whose values the result shows, as placeholders when applied and as stored otherwise; `index_columns`; and `absent_columns`, the declared names the data lacks as a column or an index level. A typo such as 'emial' therefore shows up instead of leaving 'email' quietly unmasked. summarize_categorical shows the values of its selected columns. find_duplicate_rows shows only row IDs, so its `columns` holds id_column when that column is sensitive and the result has groups.
- **Text.** A masking line follows the heading, wrapped at 120 characters. It names the masked columns and the setting that masked them, or says that the result shows no value of a sensitive column. When masking is off but the result shows values of sensitive columns, the line says so and names `mask_sensitive=True`. Without a project there is no line. Placeholders print without quotes, so `<masked 1>` can't pass for a stored label.
- **Placeholders.** summarize_categorical numbers a sensitive column's levels in level order, so its k-th level is `<masked k>` in `levels`, `most_common_levels`, `case_or_space_variants`, the text and `to_frame()` alike. Unused categories continue the numbering in category order. `label_type`, counts and shares stay. find_duplicate_rows numbers the IDs of a sensitive id_column by first appearance in the groups, and equal IDs share a placeholder, so repeated IDs still show as repeated. A missing ID stays null.
- **No raw value stays in a result.** Masking happens while the result is built. For a masked column, the private levels table behind `to_frame()` holds the placeholders' numbers as a RangeIndex, the counts in level order and the label types, and `to_frame()` writes the placeholders. A pickled or copied result therefore holds no raw value of a masked column either.
- **Index labels** are never masked, as the ticket says. When an index level is named after a sensitive column and the result shows index labels as row IDs, `masking.index_columns` names it, and the masking line says to pass a non-sensitive id_column, such as after `df.reset_index()`. Without that, the line would claim that the result shows no sensitive value. Both analyses' docstrings give agents the same advice.
- **Discovery.** `describe_analysis()` gained `shows_raw_values`, true exactly for the analyses that support masking, and prints a `Masking:` line of its own: supported, because the results can show labels or row IDs, or not needed, with the note that numeric statistics, such as a minimum, are never masked. `list_analyses()` keeps `supports_masking`. The registry gives every analysis that supports masking the tags in `_registry.MASKING_TAGS`, "masking" and "mask sensitive", so `ae.search_analyses("mask sensitive columns")` lists exactly those first; the tags avoid "values" and "columns", which questions about the data use too. The guide gained three lines on masking with the call to make. It prints 50 lines now and should print about 59 once all 11 analyses exist.
- **Contract.** A new contract test requires that an analysis supports masking exactly when it takes `mask_sensitive` and returns a `MaskableResult`, and that it then takes `project` too. A `project` alone stays possible for the dataset roles of later slices.
- **No-leak property.** `test_with_masking_on_no_value_of_a_sensitive_column_reaches_the_result` runs for every analysis whose `ae.list_analyses()` entry supports masking. `strategies.frames_with_secrets()` puts one or two sensitive columns in front of a generated frame and sometimes repeats rows, so duplicates occur. Each value of such a column holds a marker that no other generated value and no result text holds: "secret" for text (object, str, string[pyarrow] and a categorical with an unused category, case and space variants included), "918273645" for numbers in an object column and "2233-" for datetimes. Searching for the marker also catches a value that the text cuts short. The property searches the printed text, `to_json()` and every table `to_frame()` returns, as CSV. Each recipe gained `sensitive_options`, which draws arguments that make the result show the sensitive values, such as id_column, and `masking_on()` switches masking on through the project or the call. Without `sensitive_options`, 50 examples never made find_duplicate_rows show a sensitive row ID. Breaking masking on purpose in four ways (masking nothing, or leaving the `to_frame()` table, the unused categories or the case variants unmasked) failed the property every time.
- **Numbers in the property.** Numeric statistics are never masked, as the spec says, so a sensitive column of a numeric dtype could show its minimum as a raw value. The property therefore keeps its numbers in object columns, where no analysis computes statistics. Unit tests cover masked numeric and integer columns.
- **Recipes.** `recipes.masking_arguments(data)` draws `project=` and `mask_sensitive=` in every valid combination, and `with_masking(options)` adds them to an analysis's options.
- **Docs.** The README's status line names `Project` and `DataPolicy`. The catalogue marks `DataPolicy` in the type glossary as implemented, with its differences, and the summarize_categorical and find_duplicate_rows entries list the new parameters. GLOSSARY.md's Project entry now says that analyses get it where roles or the data policy matter, as ADR 0004 does.

For ticket 09:

- `Project.model_validate(dict)` builds a project from parsed TOML and raises `InvalidArgumentError` in the package's format, with code `invalid_call` for an unknown field. Catch it and raise `ProjectFileError` with the valid keys; `unknown_name_message` gives the closest match. `name` is a str or None, `sensitive_columns` a tuple of str and `mask_sensitive` a bool, and `project.model_dump(mode="json")` gives what to write. A file with `mask_sensitive = true` and no sensitive columns raises, as building one in code does.

For tickets 11, 13 and 15:

- Register with `masking=True`, which also adds the masking search tags, add `project: Project | None = None` and `mask_sensitive: bool | None = None` after the other options, subclass `results.MaskableResult`, and record `"project": project.model_dump(mode="json") if project else None` and `"mask_sensitive": mask_sensitive` in `parameters`. The contract test checks the first three.
- Call `masking = resolve_masking(name, project, mask_sensitive)` first. Where the result shows a column's values and `masking.masks(column)` holds, mask levels or classes with `mask_levels(levels)`, which gives `.label(position)` for entries, `.levels` for the `to_frame()` table and `.unused_categories`. Mask row IDs, example values or candidate values with `mask_values(values)`, one call per column with all of that column's values in result order, so that a value shows as the same placeholder everywhere. When id_column is also a column whose values the result shows, put both in that one call.
- Pass `masking.record(shown, data)` as `masking=`, where `shown` lists the columns whose values the result shows, plus None when it shows index labels as row IDs.
- In the text, print placeholders without quotes, such as with `_text.join_labels(ids, quote=False)` when `self._masked(column)` holds.
- The docstring's `mask_sensitive` entry must hold "Masking is a guardrail against accidental exposure, not anonymization or access control." With an id_column, it must also hold "Index labels are never masked", and `When to use:` must hold "pass a non-sensitive id_column". tests/test_masking.py checks this, the resolution matrix and both errors for every masking analysis, calling each with its recipe's required arguments on a frame with a "customer" column.
- Wrap the recipe's options in `with_masking(...)` and give it `sensitive_options` that make the result show the sensitive columns' values, such as id_column, target_column or the columns to check. Otherwise the no-leak property can't fail. For 15, a regression target's statistics stay unmasked by design, and the property's numbers sit in object columns, which can't be regression targets.

Measurements, on the M3 Max with Python 3.12.11 and 2 threads, while other agents used the machine:

- Default arguments are unchanged, since masking is off without a project. `uv run pytest -m benchmark` timed summarize_categorical at 1.53 s and find_duplicate_rows at 0.05 s with pandas 3.0.6 and numpy 2.5.4, and at 2.47 s and 0.05 s with pandas 2.2.0 and numpy 1.26.0.
- With all 35 text and categorical columns of the benchmark frame masked, summarize_categorical took 5.21 s against 1.54 s unmasked on pandas 3.0.6, and 6.18 s against 2.36 s on pandas 2.2.0. To number the levels, masking sorts every level of a masked column, while the unmasked call finds only the first 100. NumPy's object argsort spends about 3 s of that on the 5.4 million text labels. `to_frame()` of the masked result took 1.33 s and 1.22 s. Masking a few columns costs little. If masking every text column matters, sorting text labels with pyarrow in `_levels._full_order` would cut the sort. The first version wrote every placeholder up front, which cost 1 s more and kept 5.4 million placeholder strings, about 330 MiB with the index's pointers; now only `to_frame()` writes them.
- find_duplicate_rows on 1,000,000 rows in which every row appears twice (500,000 groups), with a sensitive text id_column, took 4.48 s masked against 3.15 s unmasked on pandas 3.0.6, and 5.52 s against 5.00 s on pandas 2.2.0.
