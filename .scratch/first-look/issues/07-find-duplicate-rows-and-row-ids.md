# 07: find_duplicate_rows and row IDs

**What to build:** An agent calls `ae.find_duplicate_rows(df)` and learns whether exact duplicate rows exist, how many groups and excess copies there are, and which rows they are. Row IDs are index labels, so `df.loc[ids]` shows the rows straight away, or values of `id_column=` when the index is a plain row number. No rows are removed. The agent decides what to do with them.

This ticket also sets the row ID rules that validate_column_types, detect_missing_sentinels and profile_target reuse. The analysis lives in `agent_eda.data.duplicates`. Masking comes in ticket 08.

Read these sections of `.scratch/first-look/spec.md`: the find_duplicate_rows entry under The first-look analyses, Row IDs, and Analysis results. Covers user stories 50 to 52, 101 and 102.

**Blocked by:** 03-property-tests-and-benchmark, 04-discovery

**Status:** ready-for-agent

- [x] The result gives the duplicate groups, each with its size and row IDs, ordered by first occurrence; the group count; the rows in duplicate groups; the excess copies, which are the rows in groups minus the groups; the duplicate share, which is the excess copies over all rows; and the compared columns.
- [x] Missing values compare equal, as in pandas, and the result says so.

## Comments

What this ticket settled that the spec left open:

- **Result fields.** `FindDuplicateRowsResult` has `compared_columns`, `missing_values_compare_equal` (always true), `duplicate_groups` (each a `DuplicateGroup` with `size` and `row_ids`), `duplicate_group_count`, `duplicate_group_row_count`, `excess_copy_count` and `duplicate_share`. Counts end in `_count` like the other analyses' counts. The rows in groups are `duplicate_group_row_count`, because `duplicate_row_count` could mean either of pandas' counts, `duplicated(keep=False)` or `duplicated()`. A group's number is its position in `duplicate_groups`, from 0. `duplicate_share` is null only for data without rows (0 over 0), with a `too_few_values` limitation. With rows but no column to compare it is 0.0, and the status says nothing was compared.
- **How values compare.** Rows compare as pandas' factorize compares values, the path `DataFrame.duplicated()` takes for two or more columns. Every missing value (None, NaN, NaT, pd.NA) equals every other, 1, 1.0 and True are one value in an object column, and 0.0 equals -0.0. NaN stored as a value in a Float64 or `double[pyarrow]` column stays apart from missing values, as pandas' `isna()` decides. For a single column, pandas uses `Series.duplicated()` instead, which tells None, NaN, NaT and pd.NA apart in an object column. find_duplicate_rows doesn't, so "missing values compare equal" holds for any number of columns, and the reference tests add a constant column to send pandas down its factorize path. Lists, dicts, sets, NumPy arrays and pyarrow lists can't be factorized, and pandas' `duplicated()` raises on them over two or more columns. Here they compare by content through a hashable stand-in from `_values.hashable_values`: dicts ignore key order as `==` does, missing values inside them are equal, and any other unhashable object compares by its type and repr. A value Python can hash keeps its own form, so it compares as pandas compares it, whatever else the column holds. The review found that an earlier version also rewrote hashable tuples, so `(1, nan)` and `(1, None)` were equal only while a list sat among the remaining candidate rows, and the column order changed the groups. A property test now checks that the duplicates among some rows don't depend on the other rows.
- **The search.** `_find_groups` carries a key per candidate row and extends it one column at a time. While the keys can tell rows apart, rows whose key no other row has stop being candidates, so later columns are read only for rows that can still repeat. On the benchmark frame, 6 columns settle every row. Once dropping removes less than a tenth of the candidates, as when most rows repeat, keys keep combining and are only renumbered before they could pass 2^62. Always dropping took 3.0 s (latest) and 4.0 s (minimum versions) on a frame where every row appears twice; this rule took 1.9 and 2.8 s in the same prototype. `_values.column_values` hands pd.factorize a NumPy array for NumPy dtypes, because pandas 2.2 warns about the wrapper that `Series.array` returns for them.
- **Statuses.** Data without rows gives `insufficient_data` with code `no_rows`; the reason is now `_run.NO_ROWS`, which `overall_status` shares. When `columns=None` leaves nothing to compare, because the data has no columns or only `id_column`, the status is `not_applicable` with code `no_columns_to_compare`. Everything else is `completed`, one row included, and only a completed run has a finding. `failed` is declared, as for the other analyses, but no path returns it.
- **Row IDs, shared with tickets 11, 13 and 15.** `_row_ids.read_row_ids(analysis, data, id_column)` checks `id_column` like any column argument, through `select_columns` with `parameter="id_column"`, so an unknown name raises `ColumnNotFoundError` with the closest names. An `id_column` whose values can't be hashed raises `ColumnTypeError` (`unsupported_column_type`), naming the dtype; `errors.py` now lists that case. It returns `RowIds`: `id_column`, `labels`, and `repeated`, which says per row whether another row has the same ID. `RowIds.at(positions)` gives the IDs as pandas gives them, Timestamps or MultiIndex tuples, so `df.loc[ids]` finds the rows. `_row_ids.duplicated_labels(labels, keep=...)` decides which IDs repeat, and describe_dataset now decides with it whether the index is unique, so the two can't disagree, as the review asked. It follows pandas' `duplicated()`, as `df.loc` does: None, NaN and NaT are three labels in an object index, while equal values, missing ones of the same kind included, repeat. Index labels that pandas can't hash work too: lists in an object index compare as `Series.duplicated()` compares them, and pyarrow lists by content. The record shows all three kinds of missing labels as null, so an object index holding both None and NaN shows two nulls without an `ambiguous_row_ids` limitation, though `df.loc` tells them apart. `select_columns(..., id_column=...)` leaves the ID column out of the default selection, while a request may name it; `left_out` still lists only the columns left out for their kind, so wording such as summarize_numeric's "Left out, not numeric or boolean" can't name the ID column. A scalar option whose name ends in `column` now takes a label that isn't a string, such as `id_column=0`, as `columns` already did.
- **Row IDs in results.** A result field holds `RowId` values (`results.RowId`, an `Annotated[Any, ...]`) and carries the `_ROW_IDS` cap of 10. The result object keeps the labels as pandas gives them, and the record converts them with `results.row_id_json`: timestamps, dates and times to ISO 8601 strings, durations to ISO 8601 durations such as `P1DT0H0M0S`, MultiIndex tuples to lists, NumPy scalars to Python numbers, missing values to null, ±inf to `"inf"` and `"-inf"`, sets to lists ordered by their items' JSON rather than by hash, dicts to JSON objects, and anything else, such as a Period or a Decimal, to its `str()`. NumPy's `timedelta64` is one of its integer types, so durations are matched before integers. pydantic's own conversion differs between 2.7 and 2.14 (it wrote `P1D` for a day) and raises on NumPy scalars and Periods, so it isn't used. pydantic 2.7 can't build a model with a PEP 695 `type` alias, so `RowId` is a plain `Annotated`. A new `_annotations.TypeName` lets describe_analysis show it as `list[RowId]` instead of `list[Any]`.
- **Ambiguous row IDs.** `_row_ids.ambiguous_row_ids(row_ids, fields)` gives the limitation whenever the index or the ID column repeats, as the ticket says, also when no row ID the result shows repeats. `fields` are the paths of the fields that hold a repeated ID, here such as `duplicate_groups[0].row_ids`; when there are none, the reason says so. The reason starts with the count and the fix, "use a unique id_column", so the printed line, cut at 120 characters, keeps both; for the index it adds `df.reset_index(drop=True)`. `duplicated_labels` reads the index through a Series over its values, or a MultiIndex's codes, so it never builds the caller's lookup table, which a test checks through the index's memory size.
- **Record and text.** The record keeps 100 groups and 10 row IDs per group, with their totals. `ResultModel._cap_growing_fields` now serializes only the entries the record keeps, through a shallow `model_copy` holding the first ones, and takes each total from the full list. Before, `to_json()` converted every row ID of 500,000 groups and then dropped them, which took 2.2 s; now it takes no measurable time. `_text.Table` gained `total`, so a result can format only the 10 rows the text shows, and `frame`, the footer's account of `to_frame()` when that isn't one row per table row ("all 5 rows in groups"). `join_labels` formats only the labels it names. The text says which columns were compared, that missing values compare equal and where row IDs come from. `to_frame()` has `group` (int64) and `row_id` (object, the labels as pandas gives them), by group, then in row order.
- **Search and docs.** Tags: duplicates, duplicate rows, repeated rows, identical rows, dedupe, deduplicate, row ids. "duplicated column labels" and "non-unique index" still find describe_dataset first. describe_dataset's `When to use:` and `See Also:` point here for rows that repeat, and the README's status line names the analysis.

For ticket 08: masking covers row IDs taken from a sensitive `id_column`. They live in `DuplicateGroup.row_ids`, which the text table, the record (through `RowId`'s serializer) and the `row_id` column of `to_frame()` all read. Index labels are never masked. The analysis also needs `project` and `mask_sensitive` in its signature and `masking=True` in its registration.

For tickets 11, 13 and 15: call `read_row_ids` before `select_columns(..., id_column=row_ids.id_column)`. Keep IDs from `row_ids.at(positions)` in fields typed `Annotated[list[RowId], _ROW_IDS]`. Collect the paths of the fields whose rows have `row_ids.repeated` set and pass them to `ambiguous_row_ids`. To compare values that may include lists or dicts, factorize `_values.hashable_values(values)` when pd.factorize raises, as find_duplicate_rows does.

- The ranges cover two runs on a quiet machine, before and after the review's fixes. While other agents' jobs ran on the machine, the same calls took up to 0.05, 2.6 and 3.7 s with the latest versions and 0.06, 3.8 and 5.0 s with the minimum ones. With an `id_column` (all-distinct text, Int64 or datetime), the benchmark frame takes 0.05 to 0.15 s on both version sets. One group of all 1,000,000 rows of a constant frame takes 0.07 to 0.09 s.
- pandas' `duplicated(keep=False)` on the every-row-twice frame takes 1.6 s with the latest versions. Most of find_duplicate_rows' time there goes to factorizing the 100 columns (1.2 s latest, 2.0 s minimum) and building the 500,000 group records: 0.4 s with pydantic 2.14 and 1.2 s with pydantic 2.7, which runs a Python-level isinstance check per group. `model_construct` was no faster.
- In the same benchmark runs, describe_dataset took 0.79 to 0.83 s (latest) and 1.75 to 2.23 s (minimum) and summarize_numeric 1.21 to 1.25 and 1.41 to 1.52 s, close to ticket 03's numbers. Sharing the index rule left describe_dataset's time unchanged.
