# 04: Discovery: describe_analysis, search_analyses and guide

**What to build:** An agent new to the package calls `ae.guide()` and gets one page on what the package does, how to call an analysis, how to read its result and which analyses exist, in first-look order. `ae.search_analyses()` finds the right analysis from the agent's own wording, such as "nulls per column", and `ae.describe_analysis()` tells the agent everything it needs for a correct first call.

All three come from the registry and the docstrings, so there's no second copy to keep in sync, and none of them loads SciPy.

Read these sections of `.scratch/first-look/spec.md`: Discovery, Docstrings, and test groups 3, 5 and 8 plus the search acceptance cases under Testing Decisions. Covers user stories 9 to 14 and 16 to 18.

**Blocked by:** 02-summarize-numeric-and-column-rules

**Status:** ready-for-agent

## Comments

What this ticket settled that the spec left open:

- **Names describe_analysis takes.** The short name and `module.name`, as the spec says, plus `agent_eda.name` and `ae.name`, the way agents write the export. An unknown name raises `UnknownAnalysisError` with code `unknown_analysis`. It suggests up to 3 names through the shared `closest_names` (case and surrounding spaces first, then difflib, on the part after the last dot), lists up to 20 analyses and points to `ae.search_analyses`. A name that isn't a string raises `InvalidArgumentError`, and when it is an analysis function the message shows the call with its name.
- **The description record.** `AnalysisDescription` in `agent_eda.results` has `name`, `module`, `summary`, `when_to_use`, `signature`, `parameters`, `parameters_schema`, `statuses`, `finding_codes`, `result_class`, `result_fields`, `shared_result_fields`, `methods`, `supports_masking`, `work_limit_parameters` and `example`, with `to_dict()` and `to_json()`. Each parameter has `type`, `required`, `default`, `allowed_values`, `valid_range` and its `Args:` text. A Literal shows as the type of its values (`quantile_method: str`) with the choices in `allowed_values`, also in the signature, which would otherwise run past 300 characters. Ranges come from the `Annotated` bounds in the words the error messages use ("0 <= trim_fraction < 0.5", "each value: 0 <= value <= 1"). Both now call `_annotations.py`, which took the annotation helpers out of `_registry.py`. The description reads the annotations the registry resolved with `get_type_hints`, so a module that writes annotations as strings still gets its choices and ranges; `AnalysisSpec.annotations` now holds data's too. Defaults are JSON values, so the signature shows the quantiles default as a list. `parameters_schema` is the registry's `arguments.model_json_schema()` with each property's `Args:` text as its `description`. pydantic 2.7 writes `"minimum": 0.0` where 2.14 writes `0`.
- **Result fields.** `result_fields` holds the fields a result class adds and `shared_result_fields` the ones from `AnalysisResult`, each with its type, its description and, for records such as the per-column entries, their fields. The text prints the added fields with their descriptions, the entry fields by name and the shared fields in one line.
- **Finding codes carry their meaning**, read from the ``- `code`: meaning`` bullets in `Returns:`. Both docstrings had them already, and the contract test now requires one for every declared code.
- **Printed description.** Lines stay within 120 characters, which a test checks for every analysis, but there is no line cap. describe_dataset prints 66 lines against its 87-line docstring, summarize_numeric 73 against 121. The example prints as code without prompts, ready to paste. A one-line output follows its statement as a comment (`res.columns["income"].median  # 58.0`), and longer output such as a printed result is left out. The record keeps the whole doctest. The masking line reads "not supported" or "supported (project=, mask_sensitive=)"; ticket 08 adds that those analyses can show raw values.
- **Search.** `limit` can go by position, as the spec writes `search_analyses(query, limit=5)`. It must be an int of at least 1 (NumPy ints work, bools don't), and the query must be a string. Words are lowercased runs of letters and digits in any script, so `_` and `-` split them, "-999" searches for 999 and "naïve" stays whole. Common words such as "the", "per" and "what" are dropped, and a plural ending goes, so "nulls" matches "null" and "categories" matches "category". `_search.SYNONYMS` maps the words agents use to the package's word: null, nan and na to missing; duplicated, dupe and dup to duplicate; associated, correlation, correlated, correlate and corr to association; label and outcome to target. The mapping goes one way, so "label" finds the target while "target column" doesn't find the column labels describe_dataset reports. A word scores the best field it occurs in: 4 for the name, 3 for a tag, 2 for the summary and 1 for the `When to use:` text. An analysis scores the sum. A query whose words, joined by `_`, spell a name puts that analysis first, and ties go to the alphabetically first name. `SearchListing` records the searched `terms` with the package's word for each, a `match_count` that includes matches beyond the limit, and each match's `score` and `matched_terms`. It prints "Searched for: nulls (also missing)", so an agent sees how its words were read, and says which `limit=` shows the matches it left out.
- **describe_dataset's tags** gained "column labels" and "duplicated column labels". With a target analysis registered, "label" as a synonym would otherwise rank it above describe_dataset for questions about column labels.
- **Guide.** The first-look order lives in `discovery.FIRST_LOOK`, with all 11 names and a few words on what each step covers. The guide numbers the steps that have a registered analysis, and its list of analyses is the printed `ae.list_analyses()`, masking marks included. It prints 34 lines today. With stand-ins for the nine planned analyses registered in a scratch script, using the spec's summary lines, it printed 55 lines of at most 114 characters, which leaves 5 lines for later additions such as masking.
- **Registry.** `AnalysisSpec.docstring` holds the docstring as `_docstring.parse` reads it at registration: the summary, the `When to use:` paragraph, the `Args:` and `Statuses:` entries, the `Returns:` code bullets and the `Examples:` doctest. Discovery reads only these and the registry. `ae.list_analyses()` gained `to_dict()` and `to_json()`, as the other two discovery records have.
- **Catalogue.** `list_capabilities` and `describe_capability` in `eda.registry` are marked implemented as `list_analyses` and `describe_analysis`, with their differences noted.

- An analysis shows up in search, the guide and `describe_analysis()` once it is registered and exported (`_EXPORTS`, `__all__` and the TYPE_CHECKING imports). Discovery code needs no change.

- Define each finding code in a ``- `code`: meaning`` bullet in `Returns:`. Keep example code lines within 118 characters, since the description prints them indented by two.
